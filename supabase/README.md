# Identity and private support database

The first migration creates member profiles, scoped staff grants, private support conversations, immutable initial messages, durable operation receipts, and audit records. Migration `20261118003457_open_account_access` changes the profile default from pending to approved account access and audits existing pending-account activation, preserving suspensions and staff grants. Confirmed email is still required for private operations; this status does not claim campus affiliation. Normal clients have read-only application table grants constrained by RLS. BTP-03 adds `affiliation_command` and `set_staff_role` alongside `open_support`, plus private draft-bound evidence uploads. See [the affiliation/staff contract and evidence](../docs/affiliation-staff.md).

## Local development

BTP-04 adds [connected listings](../docs/connected-listings.md), the `save_listing` command and a safe anonymous `browse_listings` projection. Base rows remain owner-only and client writes remain denied. Run `tests/connected_listings.sql` for 29 rollback-only authorization and validation assertions. Generated types include the applied listing schema.

Use the pinned project Supabase CLI version when package scripts are added. The scaffold was generated by CLI 2.114.0. Local Supabase requires Docker.

```powershell
supabase start
supabase db reset
```

Local Auth uses port 3107 for the application origin and requires email confirmation. Use the local mail inbox for confirmation links. The `private` schema must remain outside the Data API's exposed schemas.

## Apply and verify

Inspect the target project's tables before applying the migration. Use an isolated BeeTip development project, never another application's database. The migration has not been applied merely because the file exists.

Run `tests/identity_private_support.sql` through an owner SQL connection or a trusted SQL execution tool. The script creates synthetic users and sessions inside a transaction and rolls back all fixtures. Any failed assertion aborts the test. With `psql`, use `-v ON_ERROR_STOP=1 -f supabase/tests/identity_private_support.sql` and an externally supplied connection string. Do not commit credentials.

The assertions cover automatically active confirmed accounts, ignored user metadata authority, owner-only reads, unrelated users, staff MFA and assignment, revoked roles, revoked sessions, suspension, anonymous and unconfirmed identity, direct-write denial, exact replay, changed payload, and atomic operation/audit outcomes. The connected application harness also passed concurrent exact-retry requests through two real Auth sessions. See [development setup](../docs/development.md) for the guarded fixture lifecycle and command.

The hosted run on the dedicated development project passed all 33 assertion calls and confirmed no synthetic test users, conversations, or operation receipts remained after rollback. Security advisors reported only informational RLS-without-policy notices for the private receipt and audit tables. Those tables deliberately deny direct client access. Keep those policies absent rather than adding access to silence an informational notice. Fresh-project unused-index notices are expected until real query traffic exists.

Generate database TypeScript types from the actual migrated schema. Do not label hand-written interfaces as generated types. Verify generated output against the project's migration state before updating application clients.

## Bootstrap the first support operator

Create the operator through normal Auth, confirm its email, and enroll verified MFA. Independently review the support assignment. Use the project owner's database connection to set the operator UUID, an existing support conversation UUID, and a review reason before running `bootstrap-support-operator.sql` in the same SQL session.

```sql
set beetip.bootstrap_operator_id = 'replace-with-confirmed-operator-uuid';
set beetip.bootstrap_conversation_id = 'replace-with-support-conversation-uuid';
set beetip.bootstrap_reason = 'Approved by the named pilot owner';
```

The script refuses missing inputs, an unconfirmed or suspended operator, an operator without verified MFA, or a self-assignment. It records the owner database role and reason. It grants only the support role and the specified case membership. Staff read requests also require the current JWT to have `aal2`, an active session, an unrevoked role, and unrevoked case membership. Enrollment does not automatically upgrade an existing `aal1` session. The MFA challenge UI and routine assignment workflow belong to later staff/support issues.

To revoke access, set the grant's or conversation membership's `revoked_at` and append an audit event using the reviewed owner procedure. Do not delete evidence or grant broad access to all messages. The support queue, reply commands, notification intent, realtime, and normal assignment UI remain later implementation work.
