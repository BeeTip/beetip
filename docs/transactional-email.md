# Transactional email for the connected pilot

[BTP-11](https://github.com/BeeTip/beetip/issues/13) adds application email to durable notifications. Supabase Auth retains its [signed Send Email Hook](../supabase/functions/auth-email/README.md), recipient policy, callbacks and recovery flow. Application email opens `/account/notifications` on the configured `APP_ORIGIN`. The inbox and its targets require current authorization after sign-in. Email copy is generic and contains no conversation, order, evidence, address or token data. BTP-13 owns amendment and funding interaction changes.

## Outbox and recovery

- The existing notification intent and chat-source writes create the outbox in the same transaction. The migration backfills historical pending intents. Each summary has one source. Chat groups by recipient, conversation and UTC minute, keeps the highest sequence and waits until 60 seconds after the window closes. Claiming closes its generation to late sources.
- Preparation checks the live confirmed account and target access, assignment grant time, the event preference and the relevant read marker. Summaries use inbox reads. Chat uses the conversation cursor. Staging restrictions and permanent address suppression apply before submission. A change after the database check can race with provider submission.
- Cron calls a bearer-authenticated POST. The database claims at most 10 due rows per run with `FOR UPDATE SKIP LOCKED` and random two-minute leases. The function runs up to five submissions at a time within a 30-second function limit. Brevo requests have a 3.5-second deadline. Expired claims can be reclaimed. An expired lease after preparation leaves an uncertain submission for reconciliation.
- Explicit HTTP 429 responses retry at 1, 5, 15 and 60 minutes plus jitter, with a maximum of five attempts. A valid `Retry-After` can extend a delay up to one day. Deterministic request rejection enters the operator queue. Transport errors, unexpected responses, duplicate-key responses and crashes after preparation enter `uncertain`. Provider acknowledgment and recipient-server delivery are separate states.
- The dispatch UUID stays stable across explicit rate-limit retries. Brevo's individual-transactional changelog specifies a 15-minute window, while its current batch guide specifies 30 minutes. The worker uses the individual endpoint, quarantines ambiguity at all ages, and never relies on automatic retries within either window. The actual lifetime for the staged sender remains to be confirmed. [Individual idempotency](https://developers.brevo.com/changelog/2021/11/10) · [Batch idempotency](https://developers.brevo.com/docs/heterogenous-versions-batch-emails) · [Send API](https://developers.brevo.com/reference/send-transac-email)
- Brevo's documented bearer webhook authentication is required. The endpoint also verifies a BeeTip HMAC tag over the dispatch UUID and normalized recipient digest. Brevo's documented contract supplies no raw-body signature, so event integrity relies on HTTPS and the bearer credential. The database binds the callback to the stored destination and provider message ID, with an idempotent receipt per dispatch, provider message ID and outcome. Brevo's `id` identifies the webhook configuration. A late accepted/delivered callback can stop an unsubmitted replay. Hard bounce, invalid address, blocked, spam and unsubscribe events suppress future sends to that address. Soft bounce records the failed attempt without adding the address to permanent suppression. [Brevo webhook authentication](https://developers.brevo.com/docs/secured-webhooks) · [Brevo payloads](https://developers.brevo.com/docs/transactional-webhooks)

## Staged setup and monitoring

1. Apply migrations to the intended nonproduction project. Provision a verified Brevo sender on an owner-controlled domain with Brevo's requested DNS records and confirm DKIM and DMARC. Use a separate, restricted transactional API key for application mail. Brevo Free currently includes 300 emails per day across use cases. BeeTip reserves at most 100 application submissions per UTC day, counting attempts, to leave capacity for Auth and other activity. Confirm the account's quota/reset behavior and keep Auth and app traffic within it. Keep Vercel Hobby, Supabase Free and Brevo Free within their approved use and quotas. [Domain authentication](https://help.brevo.com/hc/en-us/articles/12163873383186-Authenticate-your-domain-with-Brevo-Brevo-code-DKIM-DMARC) · [Brevo Free limits](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan)
2. Use the server settings in [the environment example](../apps/web/.env.example). Leave `BEETIP_EMAIL_ENABLED=false` until the staged go-ahead. Set a trusted `APP_ORIGIN`, a fixed `BEETIP_EMAIL_FROM`, and a unique `BEETIP_EMAIL_SUPABASE_SECRET_KEY` with the `sb_secret_` form for the intended Supabase project. The secret uses the `apikey` header. Its underlying service role remains broadly privileged. The application exposes five hard-coded job RPC methods in a server-only module, with import and credential-use restrictions in lint. Keep all keys out of browser configuration. [Supabase API keys](https://supabase.com/docs/guides/getting-started/api-keys) · [API grants](https://supabase.com/docs/guides/api/securing-your-api)
3. Keep `BEETIP_EMAIL_AUDIENCE=allowlist` and set the exact approved addresses in `BEETIP_EMAIL_RECIPIENTS`. The list is required and enforced before submissions, including backlog. A future public audience requires explicit configuration and a Vercel Production environment. A staged Vercel project can also use that environment slot, so retain its allowlist. Independently use the Auth hook's allowlist on isolated staging where closed enrollment is approved.
4. Configure an unbatched Brevo transactional webhook at the exact origin's `/api/webhooks/brevo`. Use bearer auth with `BEETIP_EMAIL_WEBHOOK_TOKEN`; subscribe to `request`, `delivered`, `hardBounce`, `softBounce`, `blocked`, `invalid`, `spam` and `unsubscribed`. Use distinct random credentials of at least 32 characters for the worker, webhook and HMAC tag. During tag key rotation, retain the previous key in `BEETIP_EMAIL_PREVIOUS_TAG_SECRET` until in-flight callbacks have settled. Review Brevo's per-contact tracking controls and verify delivered mail uses the intended link without tracking. [Create webhook](https://developers.brevo.com/reference/create-webhook) · [Tracking controls](https://help.brevo.com/hc/en-us/articles/37113920427922-About-email-tracking-pixels-and-the-CNIL-recommendation-in-Brevo)
5. In Supabase Vault, set `beetip_email_worker_origin` to the exact HTTPS deployment origin and `beetip_email_worker_token` to the value of `BEETIP_EMAIL_JOBS_SECRET`. Apply [the opt-in Cron SQL](../supabase/setup-transactional-email-cron.sql) as a database administrator when the Vercel route is reachable and enabled. Use an approved stable origin that Supabase and Brevo can reach. Supabase Cron provides minute-level wakeups while Vercel Hobby's native scheduler is daily. Restrict Vault and `pg_net` access, since the pending request queue contains the authorization header until transmission. Verify both jobs in the Cron dashboard and check **Operasi email** for the first heartbeat. [Supabase Cron](https://supabase.com/docs/guides/cron/quickstart) · [Vault and pg_net](https://supabase.com/docs/guides/functions/schedule-functions) · [Vercel scheduler limits](https://vercel.com/i/event-driven-architecture)
6. Heartbeat monitoring starts when the opt-in Cron setup runs. The watchdog registers a failed Cron run after five minutes without a heartbeat. The operator page also shows overdue work, uncertain sends, dead letters and accepted mail missing a final callback for 48 hours. Route the Cron failure signal to the owner's approved monitor if available. The dashboard and watchdog require database access. To pause dispatch, disable the worker, unschedule `beetip-email-worker` and `beetip-email-watchdog` using `cron.unschedule`, and clear `monitoring_since` and `last_success_at` in `private.email_worker_health`. Pending deliveries remain available when scheduling resumes.

## Operator replay

Open **Afiliasi opsional dan keamanan petugas**, complete MFA as a current platform administrator, and open **Operasi email**. The queue shows up to 50 sanitized failures and the dispatch code. Filter Brevo's transactional events by the exact tag `beetip-email-<dispatch UUID>` and time range. A missing log entry alone is insufficient. If acceptance is confirmed, wait for the callback or close the case without resending. After 30 minutes, an operator who has confirmed that the ambiguous request was never accepted can attest to that result and queue a new dispatch UUID. Replay always rechecks access, address suppression, and allowlisting. The audit records the actor, prior dispatch and action. A bounced address remains suppressed through replay. Keep provider payloads and real addresses out of exported evidence. [Brevo event report](https://developers.brevo.com/reference/get-email-event-report)

An accepted delivery that still lacks a final callback after 48 hours enters the operator queue for review. Operators can close the case after checking Brevo's result. Replay stays unavailable, and a verified late delivery callback can still record the final outcome.
